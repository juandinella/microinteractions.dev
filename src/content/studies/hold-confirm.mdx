## The fill measures time

Pressing the button starts a cancelable timer, and holding for 1,200ms without letting go confirms the action. The fill moves at a linear rate because its position stands for elapsed time. Any easing would make progress look faster or slower than it is. `HOLD_DURATION` sets both the timer and the CSS `--hold-duration`, so the two can't drift apart.

The fill is a layer with its own copy of the label in a contrasting color, revealed with `clip-path`, so background and text uncover along the same edge. To recolor it, set `--hold-fill` on the button or any ancestor. It uses `--accent` when that is set, and the text color otherwise. The idle and waiting labels share a grid cell and the button keeps its width when the text changes. On completion a checkmark and a confirmation label appear, which means the result doesn't depend on color.

## Release to cancel

Letting go early cancels the timer and retracts the fill in 180ms. A new press starts from zero, even mid-retraction. The hold also cancels when the button or window loses focus, the tab is hidden, the browser cancels the pointer, or the user presses Escape.

Pointer capture keeps the release on the button when the finger or cursor drifts outside it. `touch-action: none` stops small finger movements from turning the hold into a scroll, so scrolling has to start outside the button.

Space and Enter hold for the same duration, and key repeat doesn't restart the timer. Keyboard holds and reduced motion keep the linear fill, since it carries the information, and drop the press scale and the animated reset.

The accessible name stays fixed, and `aria-describedby` explains the hold. A live region announces the confirmation, or a cancellation after more than 300ms of holding. Brief taps stay silent.

## Connecting a real action

The button emits one bubbling `holdconfirm` event after a completed hold or an accepted dialog, and that's where the action runs. Plain clicks and cancelled holds never emit it. The demo returns to idle after 1,400ms. In a real interface, replace that reset with a pending state that blocks another attempt, then show success or failure.

## An alternative to holding

Some assistive technologies activate a button with a single click and no sustained press. A click with `event.detail === 0` opens a `<dialog>` with focus on Cancel. Accepting confirms and emits the same event. The dialog also works inside sandboxed iframes, where `window.confirm()` is blocked without showing anything.

Name the action in both the button and the dialog so people know what they're confirming.
