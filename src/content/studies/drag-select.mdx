## The first row decides

Pressing a box flips it at once, and that new state becomes the drag's direction. Start on an empty box and the drag checks every row it covers; start on a checked one and it clears them. Toggling each row as the pointer crosses it would turn a mixed selection into noise. A single direction per drag stays predictable.

The drag covers a range, from the row where it started to the row under the pointer, not a trail of the rows it touched. Rows inside the range take the drag's state, and rows outside it return to a snapshot taken on press. Overshooting is harmless: back off a row and it goes back to how it was. A fast pointer can't skip rows either, because the range is recomputed from two indices instead of collected from `pointermove` events.

## A band that shows the range

While the pointer is down, a band surrounds the boxes the drag will set. It answers the question a drag raises before the pointer is released: which rows does this cover? When the drag checks, the band has an accent outline and a light fill. When it clears, the outline is neutral and the fill is gone.

It appears once the drag reaches a second row, so a plain click doesn't flash it.

The band moves on `transform` alone. Two fixed caps carry its rounded ends and slide into place; the body between them is 1px tall and stretches with `scaleY()`. Scaling vertically leaves its side borders at their width, so no frame of the animation needs layout. It follows the range in 90ms on a strong ease-out, which keeps up with a fast drag without jumping row to row.

The band and the sticky header share a stacking context created by `isolation: isolate` on the scroller, so their z-index values never leak into the page around the table.

## Selecting past the edge

The list scrolls on its own when the pointer nears its top or bottom edge, faster the deeper it goes. Because rows move under a still pointer while the list scrolls, every `scroll` event recomputes the row under the last pointer position. Autoscroll and the wheel extend the range the same way.

`setPointerCapture()` keeps the drag alive when the pointer leaves the table. Only the box column sets `touch-action: none`, so a finger on the names still scrolls. `overscroll-behavior: contain` keeps a scroll that hits the end of the list from moving the page.

## Clicks, keys, and announcements

The checkboxes stay native and own the selection. The row tint, the rounded group corners, the header checkbox, and the count are derived from them after every change. Without the script, each box still checks on its own.

A click anywhere on a row toggles its box, like a label, unless it ends a text selection. Shift+click, on the box or the row, extends from the last box changed. On the keyboard, the arrows move between boxes and Shift+arrows select a range from where the run started, the same way the drag does: backing up shrinks it. Escape undoes a drag in progress, and so does the browser cancelling the pointer.

Code around the table hears about a drag the way a form would. Each box fires `input` as the drag changes it, and `change` once when the drag ends, only if its final state differs from where it started. A cancelled drag fires no `change`. It works the other way too: code that sets `checked` and dispatches `change` gets the same row tint, header checkbox, and count as a click.

Screen readers hear the settled count from a live region once the selection stops changing, never once per row. The table's description explains the drag and its keyboard equivalent, and each box's accessible name is its row.
